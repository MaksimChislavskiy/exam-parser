# Внешнее хранилище данных и справочники

Проект отделяет код парсера от больших и изменяемых данных. Справочники,
датасет и кэш не должны зависеть от конкретной буквы диска.

## Data root

Корень внешнего хранилища задаётся переменной окружения:

```env
EXAM_PARSER_DATA_ROOT=E:/Kuzovkin-data
```

Если переменная не задана, используется `~/.exam-parser-data` вне репозитория.

```text
<EXAM_PARSER_DATA_ROOT>/
├── references/
│   ├── exams.csv
│   └── topics.csv
├── dataset/
└── cache/
```

`DataStore` не привязывает проект к конкретному диску, ОС или предмету.

## Справочники

`reference_catalogs.py` загружает иерархические CSV через `CatalogSpec`.
Для нового справочника достаточно описать имя файла и колонки ID, названия и
родительского ID. Остальные столбцы сохраняются в `raw`.

```text
exams.csv:  id / name_of_Exam / parent_of_exam
topics.csv: id / name         / parent
```

Загрузчик проверяет дубликаты ID, битые parent-ссылки и циклы дерева.

### Область классификации

Полный справочник может содержать разные предметы и типы экзаменов. Перед
отправкой в LLM он ограничивается допустимой веткой через
`ReferenceCatalog.subtree(root_id)`. Категории соседних веток не попадают ни в
промпт, ни в валидацию.

Для текущего ЕГЭ по профильной математике проверенные области:

```text
exams:  root_id=2  — математика профиль
topics: root_id=1  — Математика
```

Пробный CLI:

```text
python -m exam_parser.classification_cli tasks.xlsx --catalog exams --scope-root 2
python -m exam_parser.classification_cli tasks.xlsx --catalog topics --scope-root 1
```

## Shortlist и финальный выбор

LLM не используется как детерминированный классификатор. Один прямой выбор ID и
два независимых полных прохода оказались нестабильны на близких категориях.
Поэтому `DeepSeekCatalogClassifier` теперь разделяет поиск кандидатов и решение:

```text
задача
  ↓
shortlist из 2–3 допустимых категорий
  ↓
reasoning-выбор строго среди shortlist
  ↓
семантическая проверка
  ↓
успешный ID → кэш
```

Shortlist специально содержит разумные альтернативы: например, категорию
объекта и категорию требуемого результата или узкий и более общий подтип. Поэтому
две похожие категории сравниваются на финальном этапе даже тогда, когда первый
кандидат кажется очевидным.

Финальный reasoning видит условие, название каждого кандидата и его полную
цепочку родителей. Более глубокая или более узкая категория не получает
автоматического преимущества. Если узкий подтип добавляет свойство, степень или
частный случай, которого нет в условии, допустима более общая категория.

Если финальный выбор не проходит независимую семантическую проверку, только эта
задача получает расширенное уточнение уже по полному scoped-справочнику.

## Кэш классификации

Успешный результат сохраняется во внешнем data root:

```text
<EXAM_PARSER_DATA_ROOT>/cache/classification/<catalog>/
```

Кэш хранится по отдельным задачам, а не по целому workbook. Ключ зависит от:

- нормализованного условия задачи;
- модели;
- версии промпта классификатора;
- полного fingerprint scoped-справочника.

Поэтому изменение текста задачи, модели, prompt version, содержимого справочника
или области классификации автоматически приводит к новому ключу. `task_num` в
ключ не входит: одинаковая задача в другом варианте может использовать уже
проверенный результат.

Повторный запуск с тем же контекстом не вызывает DeepSeek для cache hit. Для
эксперимента или принудительного пересчёта используется:

```text
--refresh-cache
```

Эта опция игнорирует существующие записи, выполняет классификацию заново и после
успеха обновляет кэш.

## Новый tasks.xlsx

Лист `Tasks`:

```text
task_num | condition | image_name | solution | answer | exams_id | topics_id
```

Старые пятиколоночные `tasks.xlsx` по-прежнему читаются. Также создаётся лист
`about`:

```text
class | year | date | topic | exam_id | title | code | source_name |
is_public | source_url | description
```

При перезаписи checkpoint уже заполненный `about` сохраняется.

## Классификация готового workbook

Классификация пока намеренно не встроена в OCR-пайплайн:

```bash
uv run python -m exam_parser.classification_apply_cli \
  "output/result/.../tasks.xlsx" \
  --exams-scope-root 2 \
  --topics-scope-root 1
```

По умолчанию исходный файл не изменяется, рядом создаётся
`tasks.classified.xlsx`. Другой путь задаётся через `--output`; существующий
результат не перезаписывается без `--force`.

Для явной замены исходника:

```bash
uv run python -m exam_parser.classification_apply_cli \
  "output/result/.../tasks.xlsx" \
  --exams-scope-root 2 \
  --topics-scope-root 1 \
  --in-place
```

Даже при `--in-place` оба ID сначала вычисляются и валидируются, и только затем
workbook заменяется через временный файл. Ошибка второй классификации не оставит
Excel наполовину заполненным. Успешный кэш первой классификации при этом может
быть использован следующим запуском.

Лист `about`, условия, имена изображений, решения и ответы сохраняются.

## Следующий этап

После проверки shortlist-классификатора и кэша отдельной командой его можно
подключать к основному пайплайну. Корни допустимых областей должны определяться
из метаданных экзамена, а не вводиться вручную. OCR, классификация и Excel-экспорт
остаются отдельными слоями.
